# Task 11: worldwide sandbox billing

## Audit and implementation

The actual checkout contained no Stripe dependency, checkout API, billing tables, subscription lifecycle, webhook, pricing route or entitlement service. Task 10 had a zero-price tutor booking gate and a future payment interface only. There was no working Stripe implementation to replace. Existing Supabase sessions, independent `private.admin_users`, organization permissions, tutors and learning modules are retained.

The new implementation uses the providers' documented HTTPS APIs directly, with no additional SDK dependency. `src/lib/billing/` holds strict input/order/price contracts, exact amounts, server configuration, a common provider interface and separate `StripePaymentProvider`, `EsewaPaymentProvider` and `KhaltiPaymentProvider` adapters. Capabilities distinguish unsupported refunds/cancellation/recurrence rather than simulating them.

`/pricing` and `/checkout` offer declared billing country, NPR/JPY/USD, monthly/annual subscriptions or 30/365-day passes, configured provider options and tax-inclusive final review. Language is independent of country/currency. `/billing` provides owner-scoped payment records, access periods, in-app expiration reminders, server verification and Stripe management. `/billing-policy` publishes the sandbox access-revocation policy. `/admin/billing` reports separate provider/currency gross collections, order states, active passes/subscriptions, reversals and settlement records. Navigation, dashboard and admin links are included. EN/JA/NE/HI labels are under `Billing`; no machine translation API runs.

No price is invented or enabled by migration. Products/providers begin disabled; no merchant credentials are seeded. The owner has confirmed sandbox merchant credentials are not available. The public page therefore presents a truthful unavailable state. Real provider sandbox transactions, callbacks from provider infrastructure, authenticated hosted browser journeys and settlement reconciliation have **not** been performed.

## Data and authorization

`202610260001_multi_gateway_billing.sql` is an additive transactional migration after all 16 existing migrations. It adds 13 RLS tables: `payment_providers`, `billing_products`, `regional_prices`, `purchase_orders`, `payment_transactions`, `payment_attempts`, `payment_events`, `access_passes`, `billing_subscriptions`, `entitlements`, `refunds`, `provider_settlement_records`, `premium_requirements`.

Purchase writes derive identity from `auth.uid()` and copy price/tax/product/provider/period from the enabled database price, never client amounts. Orders have owner-scoped UUID idempotency keys, at most 20 creations per rolling day, one initiation claim and unique provider references. An active/pending premium subscription prevents a duplicate subscription order. Provider initiation is not retried automatically after an ambiguous timeout, especially for Khalti which has no assumed idempotency contract. Operators must reconcile ambiguous orders before starting a replacement payment; a claimed order without a persisted provider reference is intentionally not treated as paid.

Only the server secret role can attach provider references or apply verified proofs. It cannot be called by learners/anonymous users, even by forging user metadata. `billing_apply` atomically records unique events, validates immutable reference/amount/currency, records collections and grants entitlements. Pass activation happens once; independent renewals stack under a per-user transaction lock. Duplicates cannot extend time. Stripe authorization uses the **paid invoice line period**, not a subscription item's advanced period after a failed renewal. Old invoice periods cannot truncate newer paid access. Expiration is checked against database time, requiring no expiration job. Failed/pending payments grant nothing. No grace period is granted after paid access ends.

`billing_has_feature` unifies feature checks. `premium_requirements` can protect lessons (JLPT, business, JFT/SSW), decks, question banks, exam templates and AI scenarios. Restrictive RLS also protects child blocks/cards/questions/options. Wrapped legacy SECURITY DEFINER quiz/exam/AI entry points enforce the same requirements; private originals lose client execute privileges. Guest free practice remains permitted. The lesson page checks protected access and no longer falls back to a bundled lesson for an RLS-hidden single-row result. Previously bundled public demonstration content remains free and should not be marketed as exclusive paid content.

No existing content is silently converted to premium. Configure requirements deliberately with reviewed content. The `organizations` feature is reserved but **no organization product is sold or granted**: tenant-wide fulfillment and payer authorization are not implemented. AI purchase does not enable OpenAI calls or remove existing usage/safety limits. Metered paid AI allowances require a separate quota/ledger policy. Paid tutor bookings and payouts remain disabled by the existing Task 10 database gate. These are future extensions, not pretend purchases.

## Verification and lifecycle

- Stripe: test keys only, hosted Checkout, raw-body timestamped HMAC webhook verification (five-minute tolerance), backend session/invoice retrieval, paid renewal periods and billing portal. Cancellation schedules the end of renewal. A subscription-deleted event ends access without inventing a refund. Plan/price changes that no longer match the immutable order amount fail closed; use reviewed migration/replacement-order handling before enabling portal plan switching or prorations.
- eSewa: test ePay v2 form with server HMAC-SHA256/Base64 signatures; exact decimal NPR; unique order UUID; signed return payload validation when present; independent official status enquiry before activation. A failure redirect is also only a trigger to query real status.
- Khalti: sandbox server initiation in integer paisa with purchase-order identity; persisted `pidx`; allowlisted sandbox redirect; backend lookup validates matching `pidx` and amount. Browser query status is never authoritative. Khalti's test merchant credential is named `live_secret_key` by their documentation despite the sandbox host; put **only the test-admin key** in `KHALTI_SANDBOX_SECRET`.
- Callback and manual verification are bounded to five claims per order per minute. Stripe's authenticated webhook may bypass this limit to recover delayed deliveries. Provider requests have timeouts, no redirects, allowlisted endpoints and sanitized errors. Attempts store operation/result codes, not secrets, raw webhook bodies or customer details.

Verified full/partial refunds, reversals and disputes revoke all access from the affected order. Other purchases remain independent, with their original periods. Stripe reversals also schedule cancellation of the affected subscription to stop further renewals; failed cancellation is retried by webhook delivery. Winning a dispute does not automatically restore access: operator review is required. Unknown partial-refund values remain unknown. Provider-reference snapshots deduplicate cumulative refunded amounts; do not sum different snapshots as separate refunds. Subscription cancellation is separate from refunds. eSewa/Khalti refund initiation is explicitly unsupported pending an approved merchant contract. The Stripe adapter supports full one-time refunds, but no learner refund button or public refund-write endpoint is exposed; operators use the provider's test dashboard and verify its webhook.

Gateway redirect alone never grants access. An unpaid, cancelled, expired or unverifiable return may lead to `/billing`, but that page only displays persisted owner-scoped records. Logged-out returns require the existing login flow. The UI does not claim payment success from a URL flag.

## Taxes, reports and limits

All stored amounts are exact integer minor units; JPY has zero decimal places and NPR/USD two. Provider amounts are constructed by integer/string operations. Display formatting does not determine amounts. Regional price rows store total and included tax plus reviewed explanatory text. This is a configured **test tax breakdown**, not a jurisdictional tax engine. Stripe inline prices charge the snapshotted total; provider-issued tax invoices/rates, Stripe Tax and legally valid receipts are not configured. The local payment record is not a legal tax invoice. Test tax labels and prices need owner review.

Gross collections are grouped by provider/currency (including originally captured payments later reversed). Refund/reversal records and actual statement fees/net settlements are separate. There is no FX consolidation or invented exchange rate. Settlement fields are unknown until a verified statement is entered by a privileged operator with source/reviewer and a reconciled/unreconciled/disputed status. No provider settlement feed or CSV importer is installed. Review with the database administrator; ordinary marketplace admins have report access but no unrestricted financial table writes. Dashboard history/report lists are bounded to the latest 100 entries; add indexed pagination/date filters for larger operations. Money aggregates use PostgreSQL integer/numeric sums and exact BigInt display rather than unsafe summed JavaScript numbers.

Renewal reminders are in-app only. No email delivery, scheduled wallet reconciliation, tax service, production credentials, real charges or payouts are active. Wallet refunds/reversals can only be observed when verification is triggered again; schedule trusted periodic verification before a live wallet launch. Account deletion/financial retention needs a separate reviewed policy: financial rows use restrictive foreign keys and are not silently erased by learner deletion. Secrets stay in `.env.local`, already ignored by source control.

## Migration risks

Apply in staging after a backup and verify history. Existing data is not dropped or overwritten. The migration moves earlier quiz/exam/AI implementations into private legacy functions and creates wrappers under their original public signatures; custom callers and grants must be checked. This is a compatibility migration, not permission to drop legacy functions. Wrapper authorization and preserved guest practice are covered by regression tests. Schema/index creation takes locks. Retain order/audit history during rollback. A publishable key cannot apply this migration.
